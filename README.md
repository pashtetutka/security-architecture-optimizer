Проект формирует воспроизводимую основу для исследования и сопоставления SIEM:
преобразует официальные HTML-, PDF- и JSON-документы в структурированные сведения
об источниках событий и требованиях к инфраструктуре. Каждое утверждение связано
с документом, URL, датой получения, SHA-256 и фрагментом первоисточника.

| Характеристика | Описание |
| --- | --- |
| Решаемая задача | Снижение трудоёмкости сбора и приведения разнородной документации SIEM к единому формату |
| Область данных | Поддерживаемые источники событий и системные требования |
| Вход | Официальные документы вендоров и сохранённые снимки |
| Результат | Типизированные JSON-каталоги, перечень уникальных значений и HTML-отчёт |
| Масштаб исследования | Реестр 13 SIEM; покрытие определяется доступностью и содержанием документации |
| Текущий этап | ETL и контроль качества данных; подготовка к последующей обработке |

## Решаемая проблема

Сведения об интеграциях, версиях источников, EPS, серверных ролях и аппаратных
ресурсах публикуются в разных форматах и для разных сценариев установки.
Прямое объединение этих сведений приводит к несопоставимым результатам: варианты
названий считаются разными продуктами, минимальные конфигурации смешиваются с
рекомендованными, а отсутствие опубликованного параметра трактуется как отсутствие
поддержки. ETL сохраняет условия применимости и происхождение фактов, обеспечивая
проверяемость последующей исследовательской обработки.

## Возможности

- Получение документов по HTTPS с проверкой TLS и `robots.txt`.
- Сохранение исходных снимков и проверка SHA-256 при повторном извлечении.
- Специализированные адаптеры таблиц, PDF и публичных API вендоров.
- Единые идентификаторы источников, явные алиасы и раздельное хранение версий.
- Сохранение сценариев EPS, ролей узлов, альтернатив CPU и ОС, дисковых групп и ограничений.
- Проверка контракта JSON, отчёты полноты и диагностика неподдерживаемой разметки.
- Повторная нормализация без сети и объединение независимых выгрузок.

## Установка

Среда запуска и проверки — Windows. Требуются Git и Python 3.10 или новее.
Linux и macOS учитываются как возможные источники событий SIEM. Команды выполняются из корня репозитория.

```bash
git clone https://github.com/pashtetutka/security-architecture-optimizer.git
cd security-architecture-optimizer
python -m venv .venv
```

Активация окружения в PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip install -c constraints.txt -e .
```

## Использование

Проверка контрольного набора и создание HTML-отчёта без сетевых обращений:

```bash
python -m siem.etl check --etl data/etl/repro/vendors.json --automatic-only
```

Отчёт доступен по пути `results/etl_audit/report.html`. Каждый запуск сохраняется
в новом каталоге `results/history/check_*`; предыдущие результаты остаются доступными.

Для получения новых документов сначала просмотрите зарегистрированные адреса:

```bash
python -m siem.etl crawl --dry-run --only p12
```

Параметры сетевого сбора, дополнительных CA, объединения выгрузок и целевой
нормализации приведены в [руководстве ETL](docs/etl.md).

Пять синтетических организаций и предварительное сопоставление с каталогом SIEM
доступны в веб-интерфейсе:

```bash
python -m pip install -c constraints.txt -e ".[ui]"
python -B tools/build_v2_bundle.py --output-dir results/catalog-v2
streamlit run app.py
```

Откройте раздел «Организации». Интерфейс проверяет сохранённые снимки ETL и
показывает совпадения источников, опубликованные диапазоны EPS и вопросы к
вендорам. Это исследовательский ответ; окончательная рекомендация требует
проверки версий, условий развёртывания и неизвестных потоков событий.
Шестой готовый опросный лист находится вместе с пятью учебными организациями
в `data/scenarios/` и загружается автоматически по тому же контракту.
Для такого листа интерфейс разделяет совпадения моделей, семейств и компонентов,
показывает общие физические устройства и сценарную оценку EPS с допущениями.

## Контрольный набор данных

В рабочем контрольном наборе находятся манифест с **42 документами и 40 снимками**. Режим
`--automatic-only` использует документы с зафиксированным способом получения
`automatic_https`.

| Показатель | Только автоматическое получение | Со всеми сохранёнными документами |
| --- | ---: | ---: |
| SIEM в реестре | 13 | 13 |
| Записи об источниках событий | 1473 | 1652 |
| Профили ресурсов | 25 | 25 |
| Типизированные требования | 67 | 67 |

Несколько записей одной сущности могут описывать разные версии, нормализаторы
или способы сбора. Исторические 179 записей частичной поддержки MaxPatrol
сохраняются для аудита и исключаются флагом `--automatic-only`.

Дополнительные 30 записей Ankey извлекаются из двух таблиц официального обзора
5.2.8: 23 новых и 7 обновлённых источников. В документе указано ограничение
перепубликации, поэтому PDF не включён в Git. Порядок его загрузки и подключения
описан в [документации](docs/etl.md#дополнительный-каталог-ankey).

## Проверка качества

Для фиксации исходной точки перед архитектурной миграцией доступен отдельный
офлайн-инструмент T01:

```powershell
python -B tools/baseline.py capture --root . --output-dir results/history/baseline_20261116_01
python -B tools/baseline.py verify --root . --baseline results/history/baseline_20261116_01
```

Capture создаёт новый каталог с хешами исходников и документов, исходным
происхождением, версиями окружения и прежними экспортами ETL/опросника. Verify
проверяет целостность этих входов и сохранённых экспортов без сети. Изменённое
дерево исходников вызывает диагностируемое расхождение; новый baseline создают
в другом каталоге, прежний не перезаписывают. Ограничения распространения
фиксируются по хешу документа и не заменяются разрешением публикации.

Новый контракт `siem-catalog/2.0` находится в `src/siem/domain/`. Реальный
контрольный каталог собирается без сети в новый каталог:

```powershell
python -B tools/build_v2_bundle.py --output-dir results/history/catalog_v2_local
python -B tools/public_artifact.py --output-dir results/history/public_evidence_local
```

Чтобы выполнить ту же офлайн-проверку, что и CI, запустите
`python -B tools/verify_reproducibility.py --output-dir results/repro-verify`.
В каталоге появятся bundle, отчёт по матрице G2, аудит и сводка
`reproducibility.json`. Проверка завершается ошибкой при попытке обращения
к сети из скриптов сборки и аудита или при необъяснённом пропуске в отчёте.

Чтобы собрать bundle только из автоматически полученных снимков:

```bash
python -B tools/build_v2_bundle.py --automatic-only --output-dir results/catalog-v2-automatic
```

Если фактов нет, сборщик сохраняет диагностический bundle со статусом
`no_data` и возвращает код `4`. Интерфейс показывает причину отсутствия оценки.

Обе команды отказываются перезаписывать результат. Публичный артефакт включает
байты снимков только при явном разрешении, указанном для снимка или его SHA-256.
При текущем списке разрешений артефакт содержит манифест с числом исключений
по причинам и отчёт воспроизводимости для того же SHA-256 входного манифеста.
Полнота набора снимков указана в `replay_snapshot_set_complete`. Для полного
офлайн-воспроизведения нужны исходные снимки, доступные локально.
Схемы и валидатор проверяются командой
`python -B -m unittest tests.test_domain_contracts -v`. Для запуска с другим
bundle задайте путь к его каталогу через `SIEM_CATALOG_BUNDLE`. При отсутствии
настроенного bundle и каталога `results/catalog-v2` доступно прежнее представление.
Принятая политика G2 совпала с ручным эталоном в 298 из 299 ячеек.
Для AD DS на Windows Server 2019 в RuSIEM подтверждение сбора остаётся открытым.

Проверенная локальная сборка v2 содержит 1665 утверждений о поддержке,
25 аппаратных профилей, 66 требований и 42 документа. В неё вложено
42 снимка. Ограниченный PDF Security Capsule хранится локально, в публичном
манифесте остаются SHA-256 и причина исключения. Системное требование из PDF
доступно при отдельном локальном извлечении. Правила публикации описаны выше. Числа
фиксируются manifest каждого build и не используются как единственная гарантия качества.
Producer повторно извлекает факты из snapshot bytes: сохранённый legacy-массив
`facts` является кешем и его подмена не изменяет v2 bundle.

Сетевой `crawl` возвращает код `0` для полного результата, `3` для
`complete_with_unavailable` и `4` для `no_data`; технические исключения остаются
обычным ненулевым завершением. Офлайн-проверка не требует доступности сайтов.

```bash
python -m unittest discover -s tests -v
```

Команда `check` также запускает эти тесты; для повторного просмотра данных без
тестового прогона предусмотрен `--no-tests`. CI выполняет проверки в Windows. Реальные результаты запусков доступны по значку проверки в начале README.

Основной PDF-парсер использует `pypdf`. Проверка необязательного инструмента
`pdf-candidates` пропускается без PyMuPDF. Интеграционный тест Ankey требует
локального PDF; в свежем клоне его отсутствие явно отражается как `skipped`.
Регрессионные тесты входят в репозиторий, но не в устанавливаемый пакет.

## Границы применимости

ETL поддерживает воспроизводимую обработку контрольного набора. Автоматическое
извлечение не присваивает статус `verified` и не разрешает расчёт ресурсов без
проверки смысла, версии и условий применимости данных. Закрытая документация,
запреты доступа, противоречия первоисточников и ненормализованные разделы отражаются
в отчёте. Их актуальное состояние приведено в [аудите по SIEM](docs/vendor_audit.md).
